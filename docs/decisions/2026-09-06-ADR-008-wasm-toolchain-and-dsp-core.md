# ADR-008: WebAssembly Toolchain Evaluation & DSP Core Foundation

## Context
В рамках Wave 11 проекта виртуального измерительного стенда («Цифровой двойник осциллографа») возникает потребность в детерминированных, сверхбыстрых математических ядрах цифровой обработки сигналов (DSP), таких как:
- Быстрый статистический анализ потока выборок (Vpp, Min, Max, RMS, Mean);
- Алгоритм пикового детектирования (Peak-Detect / Min-Max decimation) для сжатия до 5 MSPS входных отсчётов в горизонтальное экранное разрешение (500–2048 пикселей/корзин);
- Быстрое преобразование Фурье (FFT), цифровая фильтрация и триггерный поиск фронта в последующих волнах.

В соответствии с правилом `GEMINI.md` (п. 9 «WASM используется только там, где benchmark подтверждает необходимость... Запрещено переносить весь application code в WASM») и требованиями Wave 11 требовалось провести строгое инженерное сравнение двух основных технологических направлений: **Rust / WASM** и **C/C++ / WASM (включая Freestanding C/WAT)**.

---

## Problem
Какой стек компиляции и ABI использовать для DSP-ядер в браузере, чтобы:
1. Обеспечить 100% воспроизводимость сборки на любой платформе (Windows, Linux, macOS) без обязательной установки многогигабайтных внешних компиляторов и системных зависимостей;
2. Минимизировать размер скомпилированного бинарного артефакта (`.wasm`), исключая runtime-библиотеки (allocator, panic hooks, formatting, metadata);
3. Обеспечить минимальный overhead границы JS/WASM при частых вызовах обработки буферов отсчётов;
4. Гарантировать строгую валидацию указателей, границ памяти и детерминированную обработку ошибок.

---

## Options Comparison: Rust/WASM vs. C/C++/WASM

| Критерий | Rust / WASM (`wasm-pack` / `cargo`) | C / C++ / WASM (`Emscripten` / `clang`) | Freestanding C / WABT (Выбранный подход) |
|---|---|---|---|
| **1. Build Complexity** | Высокая: требует `rustup`, `cargo`, `wasm-pack` (~1–2 GB инструментов), lockfiles, crate dependency tree. | Высокая: `emscripten-sdk` (Python, node, LLVM backend, emsdk env vars). Сложна в CI/Windows. | **Минимальная**: чистый `wabt` через npm (`wabt.js`). Сборка выполняется за 30 мс скриптом `pnpm run build:wasm` без внешних бинарников. |
| **2. Generated Binary Size** | 25–150 KB даже с `lto`, `opt-level = "z"`, `wasm-opt` и `wee_alloc` (из-за metadata, core panic handlers). | 20–100 KB с Emscripten JS runtime shim; ~2–8 KB с `clang --target=wasm32 -nostdlib`. | **884 байта** (чистый байт-код ядра, 0 байт мертвого кода, 0 сторонних рантаймов). |
| **3. JS/WASM Boundary Cost** | Зависит от `wasm-bindgen`: накладные расходы на маршалинг структур и строк (10–30 нс на вызов). | Минимальные при `extern "C"`, но Emscripten glue code добавляет обёртки. | **Минимальные (2–5 нс)**: прямой C-ABI с целочисленными указателями смещений в `WebAssembly.Memory`. |
| **4. SIMD Availability** | Отличная (`core::arch::wasm32`), поддерживается `wasm32-unknown-unknown`. | Отличная (`<wasm_simd128.h>` в Clang/LLVM). | Полная поддержка инструкций `v128` (Wasm SIMD Proposal) в WAT/WABT. |
| **5. Debugging** | Source maps через DWARF в Chrome DevTools, но требует настройки расширения C/C++ DevTools. | Source maps через DWARF / LLVM. | Прямой маппинг инструкций через WebAssembly Text Format (`.wat`), понятный ассемблерный листинг. |
| **6. Tooling** | Богатый (crates.io), но избыточен для 2 математических формул редукции. | Огромная экосистема C DSP библиотек (FFTW, KissFFT). | Стандартные инструменты спецификации WebAssembly (W3C WABT). |
| **7. Maintainability** | Высокая для сложных систем, средняя для 50 строк математических циклов. | Средняя: зависимость от системного тулчейна C++. | Высокая: самодостаточный код ядра на C и WAT без внешних зависимостей. |
| **8. Team Familiarity** | Требует знания Rust borrowing и `wasm-bindgen`. | Требует настройки кросс-компиляции C. | Базовый C и канонический WebAssembly; нулевой порог входа для поддержания проекта. |

---

## Decision
1. **Выбрать Freestanding C-ABI архитектуру с компиляцией через WABT (`wabt` npm package)**:
   - Исходная математическая спецификация и алгоритмический эталон документируются на языке C (`src/wasm/dsp_kernel.c`).
   - Байт-код компилируется из детерминированного WebAssembly Text (`src/wasm/dsp_kernel.wat`) с помощью `wabt` в файл `src/wasm/dsp_kernel.wasm` (размер **884 байта**) и встроенный кроссплатформенный загрузчик `src/wasm/dsp_kernel_binary.ts`.
   - Сборка автоматизирована: `pnpm run build:wasm`.
2. **Линейная модель памяти (Linear Memory Layout)**:
   - Память `WebAssembly.Memory` экспортируется модулем; начальный размер — 16 страниц (1 МБ), максимальный — 256 страниц (16 МБ).
   - `0x0000 .. 0x001B` (0 .. 27 байт): структура `SignalStats` (`min`, `max`, `vpp`, `rms`, `mean`, `sample_count`, `error_code`).
   - `0x1000 .. 0x7FFF` (4 КБ .. 32 КБ): буферы децимированных корзин (`out_min`, `out_max` для экранного разрешения до 3584 корзин).
   - `0x8000 .. 0xFFFFF` (32 КБ .. 1 МБ+): входной кольцевой/пакетный буфер отсчетов АЦП (до 250 000 `Float32` отсчетов в базовой памяти; при превышении память динамически расширяется через `memory.grow`).
3. **C-ABI функции ядра**:
   - `dsp_init() -> i32`
   - `dsp_get_input_buffer_ptr() -> i32`
   - `dsp_get_output_buffer_ptr() -> i32`
   - `dsp_compute_stats(inPtr: i32, count: i32, outPtr: i32) -> i32`
   - `dsp_peak_detect_decimate(inPtr: i32, count: i32, minPtr: i32, maxPtr: i32, buckets: i32) -> i32`
4. **Обработка ошибок**:
   - Ядро валидирует указатели (`NULL == 0`) и границы `count > 0`, возвращая отрицательные коды ошибок (`-1: WASM_ERR_NULL_POINTER`, `-2: WASM_ERR_INVALID_COUNT`, `-3: WASM_ERR_OUT_OF_BOUNDS`, `-4: WASM_ERR_INVALID_BUCKETS`).
   - TypeScript обёртка `WasmDspEngine` перехватывает отрицательные коды и выбрасывает типизированный `WasmDspError`.

---

## Why
1. **Нулевая стоимость установки (Zero-Setup Reproducibility)**: Любой разработчик или CI-сервер может клонировать репозиторий, выполнить `pnpm install` и сразу собрать или протестировать проект без установки LLVM, Emscripten, MinGW или Rust.
2. **Экстремальная компактность**: 884 байта загружаются мгновенно (встроены base64 в JS-бандл), не создавая HTTP-запросов и не увеличивая размер сборки.
3. **Прямой zero-copy доступ**: Типизированные массивы `Float32Array` создаются поверх `WebAssembly.Memory.buffer` без промежуточных сериализаций или `wasm-bindgen` прослоек.
4. **Соответствие ВКР**: Математическая физическая чистота реализации. В пояснительной записке легко представить алгоритмы на C и эквивалентный ассемблер WASM.

---

## Trade-offs
- **Преимущество**: Высокая скорость выполнения, предсказуемость тактов процессора, компактность, отсутствие раздувания зависимостей.
- **Ограничение**: Сложные библиотеки общего назначения (например, с dynamic heap allocation или I/O) потребуют собственной реализации распределителя памяти или сборки через Clang. Для текущих задач DSP (фильтры, FFT, статистика, децимация) динамическая куча внутри WASM не требуется, так как память аллоцируется статически блоками.

---

## Consequences
- Добавлен npm-пакет `wabt` в `devDependencies`.
- Добавлен скрипт `scripts/build-wasm.mjs` и команда `pnpm run build:wasm`.
- Реализованы классы `WasmDspEngine` и эталонный `JsDspEngine` в `src/wasm/`.
- Добавлен набор функциональных тестов (`tests/wasm/wasm-dsp.test.ts`) и бенчмарков (`tests/wasm/wasm-vs-js.benchmark.test.ts`).

## Benchmark Evidence
Тестирование производительности проведено на стенде (Node.js v22 / V8 JIT, Windows 11, x64) в `tests/wasm/wasm-vs-js.benchmark.test.ts`:

1. **`dsp_compute_stats` (100 000 отсчетов, 200 итераций)**:
   - **Pure JS**: 0.129 мс / вызов (Пропускная способность: **777.4 MSPS**)
   - **WASM (с учётом копирования в линейную память)**: 0.069 мс / вызов (Пропускная способность: **1449.5 MSPS**)
   - **Ускорение (WASM vs JS)**: **1.86x** (почти в 2 раза быстрее)

2. **`dsp_peak_detect_decimate` (100 000 отсчетов $\to$ 1 000 экранных корзин)**:
   - **Pure JS**: 0.085 мс / вызов (**1180.4 MSPS**)
   - **WASM**: 0.081 мс / вызов (**1241.1 MSPS**)
   - **Ускорение**: **1.05x – 1.17x**

3. **`dsp_peak_detect_decimate` на предельном потоке 5 MSPS (500 000 отсчетов $\to$ 2 000 корзин)**:
   - **Pure JS**: 0.387 мс / вызов (**1292.0 MSPS**)
   - **WASM**: 0.376 мс / вызов (**1328.8 MSPS**)
   - **Ускорение**: **1.03x – 1.08x**
   - **Доля кадра**: 0.376 мс составляет всего **2.25% от бюджета кадра 60 FPS (16.67 мс)**.
