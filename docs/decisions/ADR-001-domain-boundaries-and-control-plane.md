# ADR-001: Domain Architecture Boundaries, State Machine, and Control Plane Decoupling

## Context
Разработка браузерного цифрового двойника лабораторного измерительного стенда с цифровым осциллографом требует совмещения высокой частоты логического сбора данных (1–5 MSPS), интерактивной 3D-графики (Three.js, WebGL/WebGPU) и реактивного интерфейса управления (UI). 

В традиционных веб-приложениях состояние прибора часто привязывается напрямую к React State или свойствам 3D-объектов сцены. Это приводит к:
- просадкам FPS из-за сборщика мусора и ре-рендеров React;
- размытию ответственности и невозможности тестирования логики осциллографа вне браузера;
- невозможности переноса вычислений в Web Workers или WebAssembly.

## Problem
Как организовать доменную и управляющую модель (Control Plane), чтобы она:
1. Была полностью независима от React, DOM и Three.js;
2. Гарантировала соблюдение физических инвариантов прибора (сетки 1-2-5, ограничения смещения, защита от отключения всех каналов);
3. Реализовала детерминированный жизненный цикл через строгий конечный автомат состояний (`IDLE → ARMED → RUNNING → WAITING_TRIGGER → CAPTURED → STOPPED` + `ERROR`);
4. Позволяла запускать 100% unit-тестов в изолированном Node.js runtime без эмуляторов браузера (jsdom).

## Options Considered

1. **Вариант 1: Традиционная React-центричная архитектура (Zustand/Redux + Three.js hooks)**
   - *Плюсы*: быстрая верстка UI.
   - *Минусы*: критическое нарушение требований `GEMINI.md`, невозможность автономного тестирования ядра, смешивание Control Plane и рендеринга.

2. **Вариант 2: Чистый Domain-Driven Design (DDD) с инкапсулированным State Machine и шиной событий (Выбранный вариант)**
   - *Плюсы*:
     - Домен представлен чистыми классами TypeScript без единого импорта из UI/3D библиотек;
     - Конечный автомат состояний жестко регламентирует переходы и перехватывает ошибки;
     - Вся коммуникация с UI осуществляется через типизированные команды (`RUN`, `SET_TIME_DIV`, ...) и факты-события (`STATE_CHANGED`, `TRIGGERED`, ...);
     - Скорость выполнения тестов измеряется миллисекундами (без накладных расходов DOM).
   - *Минусы*:
     - Необходимость создания слоя адаптеров (Application Service / EventBus) между UI и доменом.

## Decision
Принят **Вариант 2**:
- Сформирована структура каталогов с изолированными слоями: `src/domain`, `src/application`, `src/rendering`, `src/data`, `src/workers`, `src/wasm`, `src/storage`.
- Реализованы доменные сущности: `Oscilloscope` (Aggregate Root), `Channel`, `Trigger`, `Acquisition`, `Measurement`, `SignalSource`, `Circuit`, `Experiment`.
- Реализован класс `OscilloscopeStateMachine` со строгой матрицей допустимых переходов и обработкой ошибок.
- Внедрена типизированная командная модель (8 команд) с обязательной валидацией входных диапазонов.
- Внедрена событийная модель и легковесный `EventBus`.
- Разработан скрипт `scripts/check-boundaries.mjs` и тесты `tests/domain/boundaries.test.ts`, гарантирующие отсутствие запрещенных импортов и циклических зависимостей.

## Consequences & Trade-offs
- **Положительные**:
  - Доменная логика готова к интеграции с Three.js (Wave 2) и воркерами сбора данных (Wave 3–4);
  - Полная воспроизводимость тестов в CI/CD;
  - Защита от архитектурной деградации на раннем этапе проекта.
- **Отрицательные / Ограничения**:
  - Разработчики не могут вызывать методы Three.js или React напрямую из домена; любые обновления графики должны происходить через прослушивание событий или адаптеры рендеринга.

- Проверка границ: `pnpm run check:boundaries` -> 0 нарушений импортов, 0 циклических зависимостей.
- Проверка типов: `pnpm run typecheck` (`tsc --noEmit`) -> 0 ошибок.
