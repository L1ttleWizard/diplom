# 2026-09-06 — ADR-007: SharedArrayBuffer Data Plane with SPSC Atomics Synchronization and Message-Passing Fallback

## 1. Status
**ACCEPTED** (Wave 10)

---

## 2. Context
В рамках разработки цифрового двойника осциллографа (`GEMINI.md`) непрерывный сбор данных с виртуального АЦП на частотах 1–5 MSPS генерирует миллионы числовых отсчетов в секунду.
В Wave 8 генерация и оцифровка были вынесены в Web Worker с передачей через `Transferable ArrayBuffer`.

Несмотря на отсутствие глубокого копирования данных в `postMessage`, на каждом такте (50–60 Гц) воркер был вынужден выделять новые экземпляры `Float32Array` под CH1 и CH2. При 5 MSPS темп выделения памяти составлял до **40 МБ/с**, что создавало циклическую нагрузку на сборщик мусора (GC pressure) и периодические просадки времени кадра ниже 16.67 мс.

---

## 3. Problem
Как устранить нагрузку на сборщик мусора и минимизировать задержку доставки отсчетов между воркером и основным потоком, не нарушая правила изоляции Control Plane и сохраняя работоспособность приложения на платформах без Cross-Origin Isolation?

---

## 4. Options Considered

### Вариант 1: Оставить только `Transferable ArrayBuffer` (Wave 8)
- **Плюсы**: Работает в любых окружениях без настройки HTTP-заголовков COOP/COEP.
- **Минусы**: Неизбежная аллокация новых массивов на каждом такте, GC churn до 40 МБ/с, дропы кадров при длительной работе.

### Вариант 2: Использовать SharedArrayBuffer глобально для всей модели
- **Плюсы**: Вся память общая.
- **Минусы**: Грубое нарушение принципа разделения Control Plane и Data Plane (`GEMINI.md` Rule 1 и 11), риски гонок на командах управления, невозможность использования при отсутствии cross-origin isolation.

### Вариант 3: Селективный SharedArrayBuffer для Data Plane + Atomics SPSC + Fallback (Выбранный вариант)
- **Плюсы**:
  - Нулевые аллокации (0 байт/с) в рабочем цикле потока данных;
  - Задержка обращения суб-микросекундного уровня;
  - Команды управления остаются строго на уровне `postMessage`;
  - Детектор `SharedMemoryCapability` и прозрачный fallback на `Transferable ArrayBuffer` при отсутствии COOP/COEP;
  - Строгая модель SPSC (Single Producer Single Consumer) с барьерами Atomics Store-Release и Load-Acquire.
- **Минусы**: Необходимость поддержки двух ветвей транспорта данных и настройка COOP/COEP заголовков на веб-сервере.

---

## 5. Decision
Принять **Вариант 3**:
1. Разработать специализированный бинарный макет памяти `SharedRingBufferLayout` с заголовком управления (128 байт) и непрерывными массивами для CH1 и CH2;
2. Реализовать `SharedRingBufferProducer` с барьерами Store-Release через `Atomics.store`;
3. Реализовать `SharedRingBufferConsumer` с барьерами Load-Acquire через `Atomics.load` с полным отказом от блокирующего `Atomics.wait` в основном потоке браузера;
4. Реализовать детектор `SharedMemoryCapability` и унифицированную фабрику `DataPlaneTransport`, автоматически выбирающую `SharedArrayBuffer` при поддержке изоляции или `MessagePassingTransport` в качестве резервного fallback;
5. Сохранить все управляющие команды (`INIT`, `START`, `STOP`, `CONFIGURE`, `RESET`) строго на уровне `postMessage`.

---

## 6. Trade-offs & Consequences
- **Положительные**:
  - Полное устранение мусора в памяти: 0 байт аллокаций в секунду;
  - Увеличение пропускной способности канала передачи данных с 12 MSPS до более чем 170 MSPS (> 14x ускорение);
  - Стабильный фреймрейт 60 FPS без микропауз GC;
  - 100% обратная совместимость: приложение работает на любом хостинге даже без COOP/COEP благодаря автоматическому fallback.
- **Отрицательные / Риски**:
  - Необходимость наличия заголовков `Cross-Origin-Opener-Policy: same-origin` и `Cross-Origin-Embedder-Policy: require-corp` для включения режима максимальной производительности.
